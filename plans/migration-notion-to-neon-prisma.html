1. Current Architecture

1.1 Data Store — Notion API

The entire application uses Notion as its only database. All cashflow entries are stored as Notion pages in a single database, accessed via @notionhq/client v5.22.0. There is no traditional SQL database, no ORM, no migration files, and no local cache beyond React Query's in-memory store.

1.2 Data Model (Notion Properties)

PropertyNotion TypeDescription
NameTitleDescription of the cashflow entry
NominalNumberTransaction amount
CategorySelectCategory name (e.g. "Transportasi", "Belanja")
DateDateTransaction date (YYYY-MM-DD string)
I/OSelectEither "Income" or "Expenses"

1.3 Categories Storage

Categories are stored as select options on the Notion data source, not as separate records. Each option has an id, name, and color. Creating/deleting categories requires updating the entire Notion data source with the full list of select options (via notion.dataSources.update()).

3. Research Findings (Latest Docs, May 2026)

3.1 Prisma Version: Use 6.x, not 7

Prisma 7Prisma 6
Removes url from datasource block Uses url + directUrl in schema.prisma
Requires separate prisma.config.ts All config in schema.prisma
Import path: ./generated/prisma/client Import path: @prisma/client
Less ecosystem support, fewer docs Mature, well-documented, GA since v5
Decision: Use Prisma 6.x. directUrl gives us the same pooling benefits without breaking changes. Upgrade to 7 later when it matures.

3.2 Neon: Two Connection Strings Required

  • Pooled URL (-pooler in hostname) → Application runtime. Goes through PgBouncer for connection pooling.
  • Direct URL (no -pooler) → Prisma CLI only. Migrations and schema introspection need a direct connection.
  • The ?pgbouncer=true parameter is no longer needed (PgBouncer 1.22.0+).

3.3 No Driver Adapter Needed

Since all API routes in this app use runtime = "nodejs" (not Edge), the standard Prisma 6 setup with Neon's pooled URL works fine without @prisma/adapter-neon. The adapter is only needed for Edge Runtime (Vercel Edge Functions, Cloudflare Workers).

3.4 Cold Start Mitigation

Neon scales compute to zero after 5 minutes of inactivity. Activating from idle takes 500ms to a few seconds and can cause connection timeouts. Add these query parameters to the connection string:

connect_timeout=15    # Seconds to wait for a new connection (default: 5)
pool_timeout=15       # Seconds to wait for a connection from the pool (default: 10)

3.5 Prisma groupBy Cannot Extract Date Parts

Prisma's groupBy() method does not support PostgreSQL's EXTRACT or LEFT() functions. For monthly and daily analytics grouping, use parameterized raw SQL via prisma.$queryRaw. This is safe because Prisma's tagged templates use parameterized queries (no SQL injection risk).

3.6 Singleton Pattern Still Mandatory

Next.js hot-reload creates new module instances in development, which would create multiple PrismaClient instances without the globalThis singleton. Each instance opens num_cpus + 1 connections by default. The recommended pattern (unchanged since Prisma 5):

import { PrismaClient } from '@prisma/client'

const globalForPrisma = globalThis as unknown as { prisma: PrismaClient | undefined }

export const prisma = globalForPrisma.prisma ?? new PrismaClient()

if (process.env.NODE_ENV !== 'production') globalForPrisma.prisma = prisma

4. Prisma Schema

// prisma/schema.prisma

generator client {
  provider = "prisma-client-js"
}

datasource db {
  provider  = "postgresql"
  url       = env("DATABASE_URL")
  directUrl = env("DIRECT_URL")
}

enum IOType {
  Income
  Expenses
}

model Category {
  id        String   @id @default(uuid())
  name      String   @unique
  color     String   @default("default")
  createdAt DateTime @default(now())
  entries   Entry[]
}

model Entry {
  id         String    @id @default(uuid())
  notionId   String?
  name       String
  nominal    Float
  categoryId String?
  category   Category? @relation(fields: [categoryId], references: [id], onDelete: SetNull)
  date       String?       // YYYY-MM-DD format — matches Notion behavior
  io         IOType?
  createdAt  DateTime  @default(now())
}
Design decisions:
  • date stored as String — matches Notion's YYYY-MM-DD string format. Avoids timezone issues with Prisma's DateTime type. String comparison in YYYY-MM-DD format is lexicographically correct.
  • notionId — tracks the original Notion page ID for cross-reference during migration. Can be removed later.
  • onDelete: SetNull on the category relation — deleting a category sets categoryId to null on related entries rather than cascading the delete.
  • @@index omitted initially — add later based on query patterns (likely on date, io, categoryId).

5. One-Time Data Migration Script

// scripts/migrate-from-notion.ts
import 'dotenv/config'
import { PrismaClient } from '@prisma/client'
import { Client } from '@notionhq/client'

const prisma = new PrismaClient()
const notion = new Client({ auth: process.env.NOTION })

async function main() {
  console.log('Fetching data from Notion...')

  // 1. Get all category options from Notion
  const dataSource = await notion.dataSources.retrieve({
    data_source_id: '101568ba-726d-4640-b39c-1e80995b0127',
  })
  const props = dataSource.properties as Record<string, any>
  const categoryProp = props['Category']
  const notionCategories = categoryProp?.select?.options ?? []

  console.log(`Found ${notionCategories.length} categories in Notion`)

  // 2. Create categories in PostgreSQL — build name → id map
  const categoryMap = new Map<string, string>()
  for (const opt of notionCategories) {
    const created = await prisma.category.create({
      data: { name: opt.name, color: opt.color },
    })
    categoryMap.set(opt.name, created.id)
    console.log(`  Created category: ${opt.name} → ${created.id}`)
  }

  // 3. Get all entries from Notion (reusing existing function)
  const { getAllEntries } = await import('../lib/notion')
  const entries = await getAllEntries()
  console.log(`Found ${entries.length} entries in Notion`)

  // 4. Create entries in PostgreSQL
  let count = 0
  for (const entry of entries) {
    const categoryId = entry.category ? categoryMap.get(entry.category) : undefined
    await prisma.entry.create({
      data: {
        notionId: entry.id,
        name: entry.name,
        nominal: entry.nominal,
        categoryId: categoryId ?? null,
        date: entry.date,
        io: entry.io as any,
      },
    })
    count++
    if (count % 50 === 0) console.log(`  Migrated ${count}/${entries.length} entries`)
  }

  console.log(`\nMigration complete: ${count} entries, ${categoryMap.size} categories`)

  // 5. Verify
  const dbCount = await prisma.entry.count()
  console.log(`Verification: ${dbCount} entries in PostgreSQL (expected ${entries.length})`)
}

main()
  .catch(console.error)
  .finally(() => prisma.$disconnect())
Run with: npx tsx scripts/migrate-from-notion.ts or bun run scripts/migrate-from-notion.ts

6.1 Analytics Replacement

The analytics module currently queries all entries via Notion and computes statistics in-memory. With PostgreSQL, we can use native SQL aggregation for significantly better performance.

Analytics QueryNew Implementation
Summary (totals, counts) prisma.entry.aggregate({ _sum: { nominal }, where: { ... } }) — Prisma native
Monthly trends prisma.$queryRaw`SELECT LEFT(date, 7) AS month, io, SUM(nominal) FROM Entry WHERE ... GROUP BY 1, 2 ORDER BY 1`
Daily net flow prisma.$queryRaw`SELECT date, io, SUM(nominal) FROM Entry WHERE ... GROUP BY 1, 2 ORDER BY 1`
Category breakdown prisma.entry.groupBy({ by: ['categoryId'], _sum: { nominal }, where: { ... } }) — Prisma native
Activity overview (heatmap) prisma.$queryRaw`SELECT DATE(createdAt) AS date, COUNT(*) FROM Entry WHERE createdAt >= ... GROUP BY 1`
Note: $queryRaw with tagged templates uses parameterized queries. Prisma sends the SQL and values separately — no SQL injection risk.

6.2 Pagination Change

Notion uses string-cursor-based pagination (startCursor / nextCursor). Prisma uses offset-based (skip / take).

// Old signature (cursor-based)
getEntriesFiltered({ pageSize: 20, startCursor: "abc123" })

// New signature (offset-based)
getEntriesFiltered({ pageSize: 20, skip: 40 })

// Server action returns:
{ entries: Entry[], hasMore: boolean }  // no more nextCursor

The React Query infinite query in components/cashflow-table.tsx changes from:

// Old
queryFn: ({ pageParam }) => fetchEntriesFiltered({ cursor: pageParam })
getNextPageParam: (lastPage) => lastPage.hasMore ? lastPage.nextCursor : undefined

// New
queryFn: ({ pageParam = 0 }) => fetchEntriesFiltered({ skip: pageParam })
getNextPageParam: (lastPage, allPages) => {
  const total = allPages.reduce((sum, p) => sum + p.entries.length, 0)
  return lastPage.hasMore ? total : undefined
}

9. Risks & Mitigations

RiskMitigation
Data loss during migration Run migration against live Notion first, verify counts match before deleting Notion code. Migration script includes verification step.
Neon cold start timeouts Add connect_timeout=15&pool_timeout=15 to connection strings. Consider upgrading Neon plan to prevent auto-suspend.
Pagination behavior change Cursor → offset/skip is a behavioral change. Should be transparent since both return page results. Test infinite scroll thoroughly.
Analytics accuracy Raw SQL GROUP BY queries must match the same logic as current in-memory JS. Verify analytics output against current Notion-based results.
Connection exhaustion in dev globalThis singleton pattern prevents multiple PrismaClient instances during hot reload. Prisma Client creates num_cpus + 1 connections per instance by default.
Connection exhaustion in prod (Vercel serverless) Neon's pooled URL (PgBouncer) handles this. Each serverless function connects through the pooler, not directly to Postgres. Up to 10,000 concurrent client connections.
Category name conflicts Categories have @unique constraint on name. Duplicate names from Notion would fail — but Notion select options are already unique by design.
